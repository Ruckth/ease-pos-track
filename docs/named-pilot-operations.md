# Named-account manual pilot

This runbook covers the text-only pilot and its first three implementation phases. Release and recovery require a deployment operator and a named backup with independent access. Keep original evidence and the reviewed manifest in an operator-controlled store outside Convex and outside every snapshot. Use synthetic records during rehearsal. The privacy and release leads supply the real approvals and evidence before enrollment.

The browser pilot uses reconciled named accounts, manual assignment and the authenticated inbox. Keep the shared staff credential, public password signup, legacy CLI writers, attachment-upload transport, public upload callbacks, retention workers, doctor, assisted recovery, AI routing, Ticket email and LINE closed. Staff identity proof has an independent sender switch.

## First launch on an empty deployment

1. **Inventory once.** With ingress and egress closed, inventory the target and candidate Projects. If the inventory confirms zero legacy customers, callers, media, outstanding grants and unresolved writes, use that single dated inventory for legacy retirement, reservations and each empty Project’s media evidence. If the target has no Projects, provision them before enabling named-pilot mode. Rehearse on a disposable target first. During authorized cutover, restrict ingress to the operator, bootstrap the named Owner in legacy mode and use the Owner’s normal Project creation flow for the pilot and isolation Projects. Record the resulting IDs and verify them against the same deployment. Close operator ingress, switch to named-pilot mode and use those IDs in the manifest. Select maintenance for rollback. A positive or uncertain result follows the applicable containment or migration steps under [Prepare and install a release](#prepare-and-install-a-release).
2. **Exercise the manual journey once.** Use two synthetic customers to check invitation, recovery, Project isolation, a text Ticket, manual assignment and a private inbox update. Reference this one recorded run from the corresponding manifest fields. Add the real identity-sender, Google, accessibility, privacy and disposal evidence before enrollment. The incident runbook and the optional T3 host qualification have separate triggers.
3. **Install and open.** The operator and backup review the manifest, verify the closed and open switch observations and check admission using steps 4–6 below. Day-to-day operations need the browser and the identity sender. Staff can use manual assignment indefinitely.

Use the restore procedure only when replacing data. The outside epoch preserves revocation, and two operators can restore access to the original customer's Tickets. An empty snapshot has no customer credentials to replace.

## Release switches

| Switch or boundary | Closed state | Browser pilot state |
| --- | --- | --- |
| `TICKET_DEPLOYMENT_MODE` | `named-pilot` | `named-pilot` |
| `TICKET_PILOT_TRAFFIC` | `closed` | `open` only after installation and verification |
| `TICKET_PILOT_EPOCH` | A new, externally generated 32-byte value encoded as 64 lowercase hex characters | Same value, independently configured and matched by the installed release row |
| `TICKET_PILOT_PREVIOUS_EPOCH` | Absent on first launch. Exact independently recorded previous epoch during recovery | Same value as during installation |
| `TICKET_PILOT_MANIFEST_SHA256` | SHA-256 of the reviewed preflight plan during recovery, then the reviewed release manifest | Exact digest of the installed release manifest |
| `TICKET_PILOT_INVITATIONS` | `false` | Remains `false` until enrollment opens. Requires the identity sender to be enabled. |
| `TICKET_PILOT_IDENTITY_SENDER` | `false` and physical egress closed | `true` only when the restricted sender is verified and its egress is approved. Keep the upload runtime at `false`. |
| `MEDIA_CLEANUP_ENABLED` | Exactly `false` | Exactly `false` |
| `TICKET_RETENTION_HOLD` | Operator hold. Any value except absent or `false` stops inbox and identity expiry | Absent or `false` unless an incident or legal hold is recorded |
| `UPLOADTHING_TOKEN`, `UPLOADTHING_SECRET`, `UPLOADTHING_APP_ID`, `UPLOAD_CALLBACK_SECRET`, `APP_PASSWORD` | Remove from the target and upload runtimes. Revoke or isolate old execution identities. | Absent |
| `LOCAL_FIXTURES_ENABLED` | Absent or `false` | Absent or `false` |
| Doctor, assisted recovery, AI routing/broker, Ticket email and LINE | Unmounted or independently disabled, workers and old credentials fenced | Still disabled |

Hosted legacy deployments require an explicit `TICKET_DEPLOYMENT_MODE=legacy` on Convex and the upload runtime. Existing local development and fixture suites retain legacy mode. A hosted deployment with missing or invalid mode fails closed. A pilot installation in the database also prevents fallback to legacy. During recovery keep every pilot marker in outside configuration, including when the snapshot predates pilot setup. Audit any older build and the physical entry points before choosing it as a rollback target.

## Hosting the pilot

Pull requests build the web application on Vercel. Merging to `main` starts a production web build. Production builds verify the public signed-out viewer query on the configured backend and the required privacy notice URLs before publication. If a prerequisite is missing, the last successful deployment continues serving. Web builds run Vite without deploying Convex. Set the public frontend URL `VITE_CONVEX_URL` only for the intended backend. At an authorized cutover the operator releases the reviewed Convex build and matching web artifact, verifies direct invitation and recovery links, and records both versions in the release evidence. [Vercel Git deployment controls](https://vercel.com/docs/project-configuration/git-configuration)

Build the pilot frontend with `TICKET_DEPLOYMENT_MODE=named-pilot pnpm build`. Set both `VITE_PILOT_PRIVACY_NOTICE_TH` and `VITE_PILOT_PRIVACY_NOTICE_EN` in the web build environment. The pilot build and Vercel production build reject a missing or invalid HTTPS URL. The controller must publish a working contact and instructions for access and deletion requests in both notices. Customers can reach the notice from Account after signing in. Exercise a request through that contact during release verification. Have the controller approve the evidence window for the Owner’s eligibility confirmation before opening invitations. The invitation expires from storage 30 days after expiry and the identity audit after 90 days. If the controller needs evidence beyond those windows, resolve its storage, access and retention before enrollment.

The release manifest must contain the approved HTTPS notice URLs in `privacyNotices.th` and `privacyNotices.en`. Inspect the actual links on the built sign-in and join pages in each language, and enter their destinations in the independent switch observation as `webNotices.th` and `webNotices.en`. Both must match the approved manifest. Record the two doctor switches (`T3_DOCTOR_ENABLED` and `T3_DOCTOR_ISSUANCE_ENABLED`) in both runtime inventories. Manual pilot admission requires both to be off.

The privacy lead must explicitly approve `identityRetention` with `challengeHours: 24`, `invitationDays: 30`, `attemptDays: 30` and `auditDays: 90`, and `inboxRetention` with `itemDays: 30`, before installation. Installation copies the approved periods into the release row. One hourly job applies the installed periods across identity and inbox records. It reads up to 64 expired records per indexed table and schedules another bounded pass if any table fills its batch. Each pass verifies open traffic, matching release lineage, approval and the operator hold. Reads hide inbox items at 30 days, independently of physical deletion. Set `TICKET_RETENTION_HOLD` before an incident or legal hold and record the setting in the inventory. Resume after the hold is released. A change to the approved periods requires an updated manifest contract and release.

### Inbox history across restore, reassignment and preferences

Every inbox item records the pilot epoch it was committed under. A fresh epoch permanently hides every item restored from a snapshot, even when the Project, Ticket and preference counters in the restored data line up with new writes. After restore, people see only items from events committed in the new epoch. An assignment item displays only during the assignee interval that created it. Reassigning A to B and back to A creates one new item for A, and A's earlier item stays hidden. Inbox lists and mark-read apply the person's current preferences, so turning a category off hides its items immediately. Each change advances that preference's generation. Turning the category back on shows only items from later events. There is no separate unread count. Each list row reports its own read state through the same check.

## Customer deletion requests and the end of the pilot

Before enrollment, the controller and release operator must agree on a UTC disposal date for pilot Ticket data. Put it in `ticketDisposal.deadline` as Unix milliseconds. Record three restricted evidence references in the same manifest: `controllerDecision`, `operatorProcedure`, and `syntheticRehearsal`. The decision identifies which records can be retained for an active purpose, the responsible person and the deletion date for each retained copy. These references and the future date are mandatory at install and open. At the deadline, set `TICKET_PILOT_TRAFFIC=closed` and close ingress and active browser sessions using the quarantine procedure below. The server also rejects new admissions and protected calls at the deadline. Complete the approved disposal and record the outcome. Extending the pilot requires a newly reviewed manifest and epoch before reopening.

1. Receive the request through the published Thai or English rights contact. Verify the requester privately and match the durable customer ID. Record the request, decision, response deadline and accountable person in the controller’s restricted register outside the Ticket system. Acknowledge the request without copying Ticket contents into email.
2. The controller decides which data to erase, anonymize or keep, including any valid hold and its review date. Explain the decision and dates to the customer. If earlier erasure is required, act on that decision before the pilot-end date. Disable the account and revoke sessions to contain access while working the case.
3. The procedure must cover the Auth identity, username/password, recovery credentials, Project memberships, invitation evidence, owned Tickets, comments, inbox, receipts and related audit rows. Preserve other customers’ records. Include operational exports, provider copies and backup expiry. Record any exception with a reason, owner and final date. Keep a restricted erasure record outside restored backups so reconciliation can reapply it before reopening.
4. For a fixed-end pilot the controller may approve disposal of a dedicated pilot deployment in full. Verify its identity, inventory and isolation, stop traffic and writers, and obtain separate authorization for that disposal. An individual request on a shared deployment needs a tested customer-scoped operator procedure. Keep media cleanup off; route historical media with continuing reservations to the storage owner. Do not use development reset for a rights request.
5. Rehearse the selected procedure with synthetic data before collection: create two customers, erase the first under the approved procedure, verify their access, credentials, Ticket data and inbox are gone or retained only as approved, verify the second customer’s expected data, and exercise backup reconciliation. For whole-deployment disposal, verify the agreed end state of both customers and isolation from other deployments. Record the evidence and exceptions before opening invitations. If the procedure cannot honor an earlier required erasure or a hold, keep enrollment closed.

## Prepare and install a release

1. Confirm the zero-user launch assumption with a read-only inventory of legacy customer accounts. If an account still uses the previous password schema, preserve the deployment and hold cutover for an explicit migration decision. If an experimental pre-release environment contains broker, evaluation or promotion records, hold that environment for a separately reviewed migration. The launch schema starts with human-reviewed rules. Historic Ticket attribution and media reservations retain their session references. Close invitations and keep public application traffic and external egress closed while preparing. Inventory direct Convex calls, browser and CLI callers, every registered HTTP route and worker, storage configuration, old pending callbacks, outstanding Ticket receipts and media reservations. Account for both an empty inventory and any identified required legacy writer. Revoke outstanding presigned upload grants or keep cutover closed until their maximum validity has elapsed. Verify old grants cannot write to the provider. A required legacy writer must have a verified, scoped replacement before retirement, or the release stays closed. Record the rollback artifact and schema compatibility, or use maintenance.
2. Check every candidate Project for historical public media and document the result. A Project with unresolved public URLs stays outside the allowlist. Verify containment against copied provider URLs, old hosts and caches. App projections cannot retract data previously downloaded. Inventory the Project IDs from the exact deployment. The manifest attaches a containment evidence reference to each one.
3. Prepare the release manifest using the fields in [the manifest schema](../shared/pilot-manifest.ts). Use opaque references to actual evidence. Record the named operator and backup, verified identity sender, named cutover, text-boundary tests, manual assignment, authenticated inbox, privacy and rights approval, and recovery and rollback evidence. The approval stays with the accountable operator. The verifier checks structure and settings. The operator checks the evidence itself.
4. Calculate the digest with `pnpm pilot:verify digest <release.json>`. Set the independent environment on the exact target while physical traffic and egress remain closed. In the switch-inventory JSON include `deploymentOrigin` and the upload runtime’s effective `uploadBackendOrigin`. Include `convex` and `uploadRuntime` objects with every [inventoried key](../shared/pilot-settings.ts), plus `disabled` and `externalEgress` as defined by [the verifier](../scripts/pilot-verify.ts). Each settings object contains its effective string values. Use JSON `null` for absent keys and the marker `"present"` if a credential is found. Keep credential values out of the file. Use a fresh observation from the target after every change. Run `pnpm pilot:verify install <release.json> <switch-inventory.json>`.
5. The deployment administrator invokes internal `pilot_release:install` with `{ "manifest": "<exact file contents>" }` using the authorized target's administration interface. Preserve exact bytes, including whitespace. This binds eligible Project IDs and the epoch to the digest. It is retryable for the same manifest. A different manifest cannot replace an installed manifest in the same epoch. Changing the approved Project set requires a new reviewed epoch and fresh authority.
6. Keep physical ingress closed while applying the planned browser setting. Re-observe effective settings, run `pnpm pilot:verify open <release.json> <switch-inventory.json>`, and check internal `pilot_release:checkAdmission` with `{ "capability": "browser" }`. Exercise real RPC and HTTP with the approved named build. Verify denied legacy paths, no media data on old Ticket detail or summary reads, no upload provider or callback traffic, correct Project and account isolation, and the manual Ticket path. Open application ingress for the reconciled cohort first. Enable regular invitations only when all release operators have reviewed the gates. If any check fails, keep traffic, invitations and egress closed.

## Before replacing data

1. Close application traffic, including direct Convex RPC, and independently close external egress. Stop workers, scheduled retention and old upload/callback handlers. Remove storage and callback credentials on the target and revoke or physically fence every surviving execution identity and its network path. Confirm prior presigned grants are revoked or expired. Set `MEDIA_CLEANUP_ENABLED` to exactly `false`. A setting or an earlier database check cannot stop a process that has already started I/O. Drain it or record its unknown outcome without reissuing it. If the platform cannot prove closure of direct calls or egress, use isolated deployment recovery with no public sessions or live provider credentials.
2. Record the exact snapshot, its installed epoch (or JSON `null` for a pre-pilot snapshot), the independently observed previous epoch, policy high-water marks or disjoint namespace, and unresolved intents, file reservations, pending purges, revocations and unknown outcomes in the external evidence. Generate a fresh epoch independently before replacement. Put the preflight plan digest in the outside settings, including `TICKET_PILOT_PREVIOUS_EPOCH`. Keep the traffic, invitation and sender switches closed. Run `pnpm pilot:verify restore-preflight <restore-plan.json> <switch-inventory.json>` against observed settings. The tool performs no network calls or database writes.
3. Only the authorized maintenance procedure may replace data after the previous checks. Missing or uncertain closure, epoch history, or reservations keeps the target closed. Preserve the snapshot and every unresolved manifest. The older data cannot open traffic or turn off the outside interlock.

## After replacing data

1. Keep all public traffic and egress closed while reconciling. Compare staff disablement, roles and subjects, customer memberships and credentials, Project and Ticket archives, restricted classifications, reservations and revocations with trusted post-snapshot evidence. Keep uncertain identities, Projects and ambiguous purge outcomes quarantined. An archived Ticket remains restorable through the usual staff command after authorized reopening. A Ticket already in `purging` needs separate ownership and provider-outcome reconciliation before it can be made restorable.
2. Invalidate all pre-recovery authorities and proofs, including browser admissions, component sessions and refresh, pending Google flows, invitations, saved codes and reset grants, personal/operator/runner keys and provider/channel grants. Advance their generations under the new epoch, reconcile immutable identities, independently reprove the Owner, and require credential replacement and fresh recovery-code enrollment for restored customers. Keep AI policies, channel workers and old tool buffers shut down. Missing authoritative identity evidence keeps that account quarantined. Do not transfer Ticket ownership during recovery.
3. Reconcile authentic late upload results through operator-only internal `uploads:reconcileLateCallback` while traffic is closed, using the current epoch, original intent and independently verified provider evidence. Supply `epoch`, `intentId`, `intentSecret` and original `file` metadata in the restricted administrator session. The old callback endpoint stays closed. A matching replay leaves the receipt unchanged. A newly reconciled orphan is reserved and queued without attaching the file or scheduling provider work. If evidence or ownership is uncertain, keep the unresolved record and investigate. Keep file and intent material out of general logs and command arguments.
4. Prepare a final release manifest with the reviewed restore plan and reconciliation evidence. Update the outside manifest digest while still closed and use the install and open sequence above. Probe old credentials and old callbacks during quarantine and again after browser reopening. Confirm fresh credentials work for a reconciled direct account and correct Project only. Leave cleanup disabled throughout this pilot. A later media release has its own storage, private delivery, credential rotation and cleanup approval.

## Named identity boundaries

Named identity ([docs/identity.md](identity.md)) enforces these boundaries through [`namedIdentityEpoch`](../convex/pilot_access.ts). A legacy or disposable deployment admits named sessions without pilot lineage. Inside a named pilot each check needs open traffic, the capability and the installed release, and returns the current epoch.

- **Sessions.** Every sign-in completion stamps its admission with the epoch (`sessionAdmissions.pilotEpoch`). Every protected call (`requireActor`, pending identity, `identity:viewer`) refuses an admission or principal from another epoch with `PILOT_STALE_AUTHORITY`. Refresh never creates admission. Closed traffic refuses sign-in before any credential check.
- **Principals.** Staff and customers carry the epoch they were enrolled or reconciled into (`pilotEpoch`). Staff accepted from an invitation, customers who sign up and the bootstrapped Owner are stamped when created. Principals that predate the epoch, including every principal in a restored snapshot, cannot sign in, recover or receive routing work. The operator runs internal `identity:reconcilePilotPrincipal` with `{ "epoch": "<current>", "staffId": "…" }` or `{ "epoch": "<current>", "customerId": "…" }` only while traffic is closed and only after checking the trusted post-snapshot evidence. Reconciliation advances the generation, revokes every session and drops a customer's saved recovery code, so the customer saves a new one after signing in. After a restore, the single-operator command refuses every customer. Two operators must approve replacement of the customer credential before the account can re-enter the pilot. [Restore and recovery instructions](identity-recovery.md)
- **Flows and invitations.** Google flows and staff and Project invitations are stamped at issue and usable only in the same epoch. Issuing and redeeming an invitation needs capability `invitation`. A Project invitation is limited to the release's Project allowlist. Challenge delivery (`identity:issueChallenge`) needs capability `identitySender`.
- **Projects.** Ticket, assignment, inbox and membership reads use `projectInDeployment`/`activeDeploymentProject` beside normal ownership and membership checks. Creating Projects, retention health, media and upload callbacks stay legacy-only. `pilot_release:ticketCapabilities` runs under the named actor policy, and both composers and staff navigation use it.
- **T3 keys.** Doctor keys keep their own `T3_DOCTOR_EPOCH` and staff generation binding. The holder must also be reconciled into the current pilot epoch.
- The shared staff password, public signup, raw-token sessions and email-based membership editing no longer exist.

## Disposable verification

Run `pnpm test:convex tests/convex/pilot-boundaries.test.ts tests/convex/inbox-intervals.test.ts` and `pnpm test:one tests/pilot_verify.test.ts tests/ticket_draft.test.ts`. The Convex harness seeds synthetic historical state, leaves the earlier installed release row, queued purge and orphan reservations in place as the snapshot state, and rotates only the outside settings. It checks missing and stale evidence, original callback rejection, restricted history replay, zero provider construction, retained reservations, archived Ticket restoration and fresh-epoch admission alongside old-epoch denial. The operator verifier also exercises two independently observed runtimes and a deliberately incomplete release. The tests sign in through the real named endpoints (customer password and the Google completion seam with its one-use flow). They show that pre-pilot sessions, flows, invitations and unreconciled principals are refused, that reconciliation and fresh sign-in admit them, and that sessions and saved codes from a restored epoch stay dead. They also show that restored inbox items stay hidden in the new epoch, and that expiry stops under closed traffic, quarantine, a release without approved periods and an operator hold. Real Google, real component refresh and provider/hosting closure need their own release evidence.
