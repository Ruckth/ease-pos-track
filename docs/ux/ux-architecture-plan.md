# Ticket workspace UX plan

This document records the design-stage audit. The application implementation, production bundle comparison and final browser checks are described in the pull request. The offline preview keeps its original sample data and behavior.

A customer with a short issue should be able to open New Ticket, type a title and submit. A staff member processing a queue should be able to open the first Ticket, take an action and move to the next Ticket with the list still in place. These are the two journeys that determine the layout.

[Open the interactive workspace](./ux-architecture-preview.html). The file runs offline with fictional Tickets. The role switcher belongs to the demonstration. In the application, the authenticated session determines the role. The audit below applies to the prototype. Implementation references use the application at commit `f745763` on November 18, 2026.

## Audit outcome

**Eight of eight categories reached 9/10 in the independent prototype review.** A separate agent fixed the workspace. The reviewer reran the original tasks on the revised HTML and returned the final scores after checking the remaining language, pin selection, search announcement, waiting order and edit-conflict cases.

In comparable staff list views at 728 × 900, the first Ticket moved from 522 to 264 CSS pixels from the top. The count of visible interactive elements fell from 24 to 17. Both measurements use the same unselected list and count visible buttons, disclosures, inputs, selects and links intersecting the viewport. They measure layout density. No participant completion-time or satisfaction data were collected.

Run `pnpm exec node docs/ux/verify-preview.mjs` in this worktree to replay 13 browser scenarios against the local file. The checks count activations, exercise browser history and role boundaries, and measure the list, detail and composer at 320, 390, 640, 728, 1024 and 1440 CSS pixels. They also cover keyboard-only operation, retry with a saved pin, conflicting edits, customer deletion and staff restoration. Account and sign-in demonstrate Thai and English. The sample Ticket workspace uses English. Production validation still needs Thai workspace tasks, assistive-technology sessions and real staff and customers.

## Audit criteria

The independent reviewer scored the November 12 prototype before the fixes. A score of 6 indicates a broken path or a loss of work, 7 indicates a detour or repeated decision, and 8 indicates a usable path with an ambiguous control. A 9 requires the important task in that category to work end to end, with the listed checks passing. The remaining point requires evidence from representative staff and customers using their own tasks and devices.

| Category | Original → revised | Original finding | Verified criterion |
| --- | ---: | --- | --- |
| Navigation and wayfinding | 6 → **9** | Back in Focus immediately opened the first Ticket again. The URL recorded the view variant alone. | Exit all three views. Restore a searched or filtered Ticket through browser Back, Forward and reload. An inaccessible Ticket reference offers a way back. |
| Task efficiency | 7 → **9** | The direct status action was fast. Changing urgency could move a Ticket under the pointer before the next action. | Send a text-only Ticket in two activations, inspect three in three and advance a visible Ticket in one. Preserve neighbors while editing urgency. |
| Visual hierarchy | 7 → **9** | The sample navigation repeated New Ticket, and the layout chooser, status filters and product actions competed with the list. | Start with a clear heading, visible Project and one primary creation action. Keep comparison tools secondary. A phone shows one working surface at a time. |
| Language and action clarity | 8 → **9** | Add pin displayed an explanation. The locale selector implied that the whole workspace would change language. | Each working control produces its named result. Describe simulations before activation. State actions name the destination or the action that leads there. |
| Responsive layout and touch | 7 → **9** | Reset measured 34 CSS pixels high, view buttons 36, and several detail disclosures 34. | Hit targets measure at least 44 × 44 CSS pixels. Check narrow, intermediate and wide displays, plus the effective narrow viewport produced by zoom. Text and actions remain reachable. |
| Keyboard and accessibility | 6 → **9** | Rebuilding the visible view could lose focus. Pin placement lacked a working keyboard path. | Use Tab, Enter, Space, arrow keys where documented, and Escape for create, details, pins and recovery. Focus returns to a visible control. Result and error text are available to assistive technology. |
| Drafts and recovery | 6 → **9** | Create drafts survived closing. Failed saves had no demonstrated recovery path, and a hidden edit could resurface in a different role. | Keep entered text and optional evidence after validation or a rejected save. Resume a closed draft, explicitly cancel edits, and undo a reversible action without rolling back another Ticket. |
| Role and workflow integrity | 7 → **9** | Customer mode could resume the sample staff member’s unsaved description on the same Ticket. Undo lived outside the active role. | Customers see their own Tickets and actions. Switching roles isolates drafts and Undo. Archived Tickets are read-only with staff Restore. A customer reply leaves status control with staff. |

In the original file, a 728 × 900 viewport showed 30 button or disclosure targets above the fold, counting controls that intersected that viewport. Chromium also reproduced the Focus Back loop and the disclosure of an unsaved fictional staff edit after switching to customer mode. Those checks exercised the previous HTML artifact.

## Navigation budget

Count a click, tap or keyboard activation that invokes a control. Start signed in at the appropriate workspace with the correct Project and relevant Tickets visible. Typing, field focus, scrolling, and the operating system’s file chooser are excluded. These counts describe the named paths. Completion time and perceived effort require observation with users.

| Task | Application path at the audited commit | Proposed path |
| --- | --- | --- |
| Send a customer Ticket with a title | New Ticket → Next → Skip for now → Submit, **4**. Selecting the unlocked Review step directly takes **3**. | New Ticket → Submit, **2** |
| Inspect three Tickets in order | Open → Close → Open → Close → Open, **5** | Open → Next → Next, **3** |
| Advance a new Ticket | Click its summary action, **1** | Acknowledge, **1** |
| Resolve an In progress Ticket | Open → Done, **2**. Desktop also supports directly dragging between lanes. | Resolve, **1** |
| Read Ticket and annotation activity | Open → expand each of the two feeds, **3** | Open → History, **2** |
| Change a description | Open → Edit → Save, **3** | Open → Edit → Save, **3**. The improvement is finding the description before media and properties. |

### Production boundaries

- **Read only the needed rows.** Staff lanes and the customer list initially fetch 20 summaries per page. Staff lane totals are Project-wide. Customer status counts reflect their loaded, owned rows. Search returns up to 50 matches and a flag indicating more. A globally urgency-ranked cross-status queue requires an indexed read and stable cursor. For a first release, rank the loaded subset and label its scope. Keep loading and empty results distinct. See `convex/domain/reads.ts` and `src/features/tickets/adapter.ts`.
- **Keep the queue stable.** An edit to urgency updates the displayed score. The next Ticket should still be the one the staff member saw before that edit. Capture the visible traversal order, skip inaccessible items, and offer an explicit re-sort. If the last loaded neighbor is reached, expose Load more or the end of the available results.
- **Preserve draft ownership.** `DisposableTicketDraft` already owns the Project, text, files, object URLs and annotations. `useComposer` preserves that owner while the form is closed. Reuse this behavior when retiring the wizard. The existing owner releases resources on removal, success or disposal. File lifetime was an open risk in the earlier plan and now has dedicated regression coverage.
- **Keep retry identity.** The existing browser submit path distinguishes definitive rejection from an unknown write outcome. Reuse recorded files and the request identity for reconciliation. A definitive conflict can prepare a new key for the next explicit submit. Cancellation can queue guarded cleanup. Describe the known outcome to the user. See `src/lib/ticket-submit.ts`, `shared/upload-receipt.ts` and `tests/ticket_draft.test.ts`.
- **Restore context safely.** Use the existing role paths and Project query parameter. Represent view, filter, permitted search and selected Ticket in navigation state. On selection, resolve the Ticket against the active Project and authenticated role. Validate return targets during sign-in. Back closes detail, Forward restores it, and Next walks the same results. Keep writes and drafts out of browser history. A fresh session must recheck permissions, including membership changes.
- **Keep role-sensitive history explicit.** Each existing activity feed returns up to 30 recent events. Public responses omit actor identity and can include before/after urgency metadata. Specify the intended customer projection before merging histories. Add server projection tests if urgency is staff-private. Show neutral activity descriptions when a verified actor label is unavailable.
- **Preserve retention behavior.** Staff Restore can clear a blocked purge while an archived Ticket is still restorable. Re-archiving begins a fresh 30-day window. Queueing cleanup and confirming provider deletion have distinct meanings. Keep version guards and operations policy in existing domain operations. The prototype represents archive and restore with local sample data.
- **Future messages require backend work.** A staff question and transition to Waiting should persist atomically. A customer can read and reply to a question on an owned Ticket. Save the reply separately from its description and keep the status Waiting until staff resumes work. Define message identity, authorship, retry behavior and read permissions before enabling this in the application.

## Delivery and validation

1. **Shorten creation and simplify both home screens.** Reuse the existing draft owner and operation adapters. Keep capture, annotation, cleanup and retry behavior throughout the switch. On the phone, test title-only creation and evidence-first creation in Thai and English.
2. **Add the queue and shared detail.** Start with an accurately labelled page of results. Preserve the existing Board as a view choice. Deliver shared Back/Next behavior, scoped editing, searchable archive and a recent timeline. Exercise pagination, permission loss, concurrent updates and browser navigation in a disposable local environment.
3. **Evaluate the default with staff and customers.** Ask staff to find a waiting Ticket, resolve another and inspect three in sequence. Ask customers to submit a short Ticket, add an image note and recover an interrupted edit. Observe the first action, wrong turns, completion time and requests for help on each device. Record language and input method. Choose the default view from these observations.
4. **Add the message workflow separately.** Test request, reply, retry and explicit resume across both roles. Keep the existing five Ticket states. Preserve the rest of the Ticket when a response is retried.

Repository verification uses `pnpm check`. Production browser workflows use `pnpm test:browser` with the disposable local backend documented in the repository. The standalone preview exercises sample state in a browser without credentials.
