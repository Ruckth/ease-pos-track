# Image uploads for Tickets and hosted pages

Ease POS uses browser canvas, orientation-aware decoding and product-specific bounds. Its newer ingest implementation uses sharp to validate uploaded bytes and its browser implementation can load a WebP WASM fallback. Ticket uploads reuse contain-fit, byte limits and encoder capability checks. The Ticket screenshot keeps its aspect ratio and alpha. [Compared Ease checkout][old-client] · [Ease POS browser source][client] · [Ease POS ingest][ingest]

## Where to encode

| Option | Fit for Ticket publishing |
| --- | --- |
| Native canvas | First choice for an optional still-image transform before upload. Use `toBlob`, check its actual type and size, and fall back to the validated original when the encoder fails or grows the file. Browsers can return PNG for unsupported output types. A worker using `OffscreenCanvas.convertToBlob` moves drawing and encoding off the UI thread. Feature-detect both APIs. [HTML canvas standard][canvas] |
| Sharp/libvips | Best fit for Node CLI preprocessing or a bounded server ingest action when every caller needs the same decoding policy. Check dimensions and frame count, cap decoded pixels and concurrent jobs, and require a successful decode. Header metadata alone does not read the compressed pixel data. Budget for native dependencies and server CPU. Server-only encoding saves storage and delivery bytes after the original upload. [Sharp][sharp] · [Input metadata][metadata] · [Decoder limits][limits] · [Convex runtimes][runtimes] |
| WASM codec | Useful when a required output codec is missing from native canvas. Load only the needed codec on demand in a worker. This adds a module download, initialization and a pixel buffer. For optional compression, retaining a valid original avoids that cost. [Ease fallback][client] · [jSquash codec packages][wasm] |

## Selected implementation

- **Browser.** Ticket uploads are prepared before uploading: native encoders run in a worker where supported, processing stays sequential, and the prepared File is cached for selection retries (a failure is evicted so the next submit prepares again). Local drafts use object URLs for immediate previews. The canvas encoder's returned MIME type determines whether the browser supports a candidate; the probe canvas needs a rendering context first, because an `OffscreenCanvas` without one cannot encode at all (before this was fixed, every image prepared in the worker, which handles files of 128 KiB or more, ended up as PNG unless its clean original could be kept). Chromium tags canvas JPEG and WebP output with its sRGB profile; untagged images display as sRGB, so the profile is removed and the pixel comparison confirms nothing changed. Hosted pages send originals for server conversion when they fit the 10 MiB page limit, because Chromium's canvas has no AVIF encoder and its 4:2:0 WebP and JPEG rarely beat an existing screenshot JPEG within the strict comparison. Larger page selections use the browser preparation above, so oversized originals never cross the network.
- **Node.** Use sharp/libvips for the CLI and for hosted-page originals sent without a prepared-image policy (the browser panel and other API clients). Separate image files convert in parallel Node actions; embedded images in one HTML document convert in batches of up to four within a 12-megapixel decoded budget. Normalize orientation before fitting within 1920 × 1080. Compare JPEG, WebP and AVIF with a lossless baseline at the resized resolution. Never send transparent pixels through JPEG. An already clean PNG, WebP, GIF or JPEG at its original size can win. When metadata can be removed from a JPEG, PNG or WebP without re-encoding and without changing the displayed pixels, that smaller copy is compared as well, so a file at its original size does not grow just to lose its metadata. A candidate must both reduce bytes and pass the pixel comparison against the reference.
- **Pixel comparison.** Shared by browser and Node (`pixelPolicy` in `shared/image-optimization.ts`). Alpha must match exactly and the mean squared error stays at most 12 per channel. Screenshots, documents and UI keep the strict rule: every channel of every pixel within 24 levels, so small text and one-pixel edges cannot blur or change colour. Opaque photographic content (fewer than 60% of neighbouring pixels identical; photos we measured were at 4–52%, screenshots at 78–95%) may instead shift the colour of up to 0.5% of pixels further, as 4:2:0 chroma subsampling does around small saturated details, while brightness still stays within 24 levels on every pixel. A 2000 × 1400 photographic fixture became a 2.6 MB PNG in Chromium under the strict rule and is now a 350 KB JPEG; three real 2.3–3 MB iPhone photos become 140–220 KB WebP in the browser worker.
- **Validation.** Check dimensions before allocating the raster, constrain input bytes and decoded pixels, and validate prepared image bytes on the server. Prepared bytes must be clean containers (`shared/raster-structure.ts`): JPEG segments are parsed through the end marker, which must be the last byte, and only frame, table, scan and a thumbnail-free JFIF header are allowed; PNG chunks must have valid checksums and be among IHDR, PLTE, tRNS, IDAT, IEND, sRGB, gAMA, cHRM, pHYs and the APNG frame chunks, with APNG frames numbered in order, inside the canvas and matching the declared count; WebP allows only VP8/VP8L/VP8X/ALPH/ANIM/ANMF with no profile, EXIF or XMP flags, and every animation frame must carry a valid bitstream inside the canvas; GIF allows only images, frame timing and the loop count, ending at the trailer; every ICO variant must be a clean PNG or an uncompressed bitmap of exactly its declared size, tiling the file; AVIF must be a still AV1 image without EXIF/XMP items or an embedded ICC profile. Node then decodes every frame with Sharp without warnings and requires no reported metadata. The browser, CLI and server all check their own output this way before uploading or storing it; server-converted embedded page images are validated like client-prepared ones; the CLI also runs the full Sharp validation, because staff uploads are recorded with the staff session rather than through the provider callback. UploadThing callbacks verify provider bytes before recording the receipt. A provider read that fails is retried twice; if the bytes still cannot be read, the receipt is recorded as rejected so existing ownership-guarded cleanup owns the file and the submission fails and can be retried. [Sharp input options][limits] · [OWASP][owasp]
- **HTML.** Keep authored filenames and relative paths. Store the detected media type separately. For UTF-8 HTML, use parser source offsets to replace literal base64 raster image sources. Scripts, URLs, CSS and other author content remain intact. Packaged assets also work from nested folders. The PNG fallback preserves exact UI pixels when no smaller supported browser encode meets the quality threshold.
- **Larger pages.** When a payload exceeds the inline budget for a Convex Node action, pass bounded private database chunks between runtimes. Reading consumes each chunk. An interrupted transfer expires after 15 minutes. The published bundle retains its existing 10 MiB limit. [Convex runtimes][runtimes]
- **Caching.** Store optimized bytes once, and honor revalidation using a private ETag on hosted images. Every conditional request rechecks the Ticket and publication state, including revoked links, before returning 304. HTML remains no-store. [HTTP caching][cache]
- **Animations.** A GIF, APNG or WebP counts as animated only with more than one frame, so a single-frame GIF is prepared like any still image. Animations within Full HD keep their own bytes minus metadata, so frame count, delays and loop count are unchanged. Over Full HD, Node resizes GIF and WebP animations to lossless animated WebP and checks that every frame, delay and the loop count survived. The browser has no animated encoder, and libvips cannot write APNG or animated AVIF; those cases, and animated AVIF anywhere, fail with `IMAGE_ANIMATION_UNSUPPORTED` and their own message.
- **Formats.** JPEG, PNG, WebP, AVIF, GIF and ICO are accepted. HEIC/HEIF is recognised but only Safari decodes it in the browser; other browsers report `IMAGE_FORMAT_UNSUPPORTED` with a message to export JPEG or PNG. Sharp's prebuilt binaries decode only AVIF from the HEIF family, so the CLI converts HEIC with macOS `sips` before preparing it and reports `IMAGE_FORMAT_UNSUPPORTED` on other platforms; server-converted hosted pages report `PAGE_IMAGE_INVALID`. BMP, TIFF and SVG are not accepted.
- **Boundaries.** Full HD means at most 1920 pixels wide and 1080 high, including portrait images. ICO containers retain their variants (PNG variants lose their metadata); resizing icons as a single raster would discard them. Colour profiles are removed from stored images: stills are compared after conversion to sRGB, and an animation kept at its own size loses an embedded profile without a comparison, which can shift wide-gamut colours slightly. Perceptual checks at the target resolution cannot recover detail lost when downsizing an unusually large screenshot.

**Residual limits.** The photographic test is a heuristic: a screenshot dominated by a photo can get the photo tolerance, and a very flat photo keeps the strict rule (and may stay lossless). Sources over 40 megapixels (some 48–50 MP phone modes) are rejected rather than downscaled. Browser tabs still running an older bundle can upload images the callback now rejects. Sharp loaded through `externalPackages` is tested on the local backend only. APNG frame data is checked structurally, not decoded, because libvips draws only the first APNG frame.

The nine-screenshot Thai sample went from 1,400,891 to 943,879 bytes through the CLI (32.6% smaller): five screenshots became WebP (37–59 KB from 103–134 KB) and four stayed JPEG because no candidate was both smaller and faithful. The server conversion used by the browser panel stores the same 943,879 bytes. Browser-side canvas preparation keeps all nine as metadata-free JPEGs (1,399,051 bytes): these are screenshots, so the strict comparison applies, and Chromium's 4:2:0 candidates shift the colour of up to 0.1% of pixels by up to 56 levels around coloured text. All nine keep their 1400 × 1050 or 416 × 900 dimensions. On the local backend, publishing took about 3 s before and 4–11 s after across runs (19.6 s before embedded images were batched), because the server now encodes instead of storing pre-encoded bytes. Savings depend on the available codecs and source images.
