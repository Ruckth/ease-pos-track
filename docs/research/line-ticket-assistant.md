# LINE Ticket assistant research

The first implementation uses Gemini directly with `gemini-4-neon`. An Owner tests and saves one Project connection, then enables an approved LINE chat. Staff review a suggestion and can create or close a Ticket and queue the reply in one action. The [interactive preview](line-ticket-assistant-preview.html) uses synthetic data.

## What the merged app already does

PR #25 added multiple bots per Project, encrypted LINE credentials, fixed webhook URLs, and staff approval of chats. The webhook verifies the signature and destination, deduplicates lifecycle events, and drops message events. Staff configure webhook use, redelivery, and group access in LINE. The named-account pilot disables LINE settings, webhook intake, and workers. ## Build sequence

1. **Setup.** Default to Gemini and the documented model ID. Test a synthetic text request, image, and PDF in one submit. Show distinct results for credentials, model access, quota or billing, and invalid output. Save a replacement encrypted key only after the test passes. Persist masked connection metadata and audit changes. For a new bot, reuse LINE's test and endpoint registration, read the URL and active status back, and link directly to console steps for redelivery, group joins and auto-replies. [Webhook settings](https://developers.line.biz/en/reference/messaging-api/#webhook-settings) · [Redelivery](https://developers.line.biz/en/docs/messaging-api/receiving-messages/) · [Group setup](https://developers.line.biz/en/docs/messaging-api/group-chats/) · [Auto-replies](https://developers.line.biz/en/docs/messaging-api/building-bot/)
2. **Intake.** Accept requests only from approved chats with the assistant enabled. Start with bot mentions in groups and direct requests in opted-in 1:1 chats. Accept follow-up attachments in a short window scoped by bot, chat, and sender. Verify the signed raw body and persist each accepted event once before acknowledging. Fetch files promptly using the LINE message ID, since LINE publishes no guaranteed availability window. Start with PNG, JPEG, and PDF. Proposed limits are two files, 8 MB per file, 12 PDF pages, and 24 hours of private staging. Honor unsend for pending input and route expired or unsupported files to manual review. [Signature](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/) · [Message events and unsend](https://developers.line.biz/en/docs/messaging-api/receiving-messages/) · [Content API](https://developers.line.biz/en/reference/messaging-api/#get-content)
3. **Review and act.** Ask the model for a typed create, close, clarify, or skip suggestion with evidence. Check the output and resolve references server-side. Reuse the Ticket domain's validation, idempotency, version checks, and auditing. Record the staff approver and LINE provenance. Use the approved customer mapping where present and the existing staff ownership policy otherwise. Closure sets an active Ticket linked to the same Project and chat to `done`, with its expected version. Save the change and enqueue the approved reply in one transaction. [Ticket operations](../../convex/domain/operations.ts) · [Ticket status and lifecycle](../../convex/schema.ts)
4. **Deliver.** Use push for the reviewed outcome because LINE reply tokens are short-lived and single-use. Recheck the current chat enrollment, send only to the originating chat, and record LINE acceptance separately from delivery. Use the same LINE retry key and payload for recoverable failures within the 24-hour window. If the outcome is still unknown after that window, surface it for staff review. [Reply](https://developers.line.biz/en/reference/messaging-api/#send-reply-message) · [Push](https://developers.line.biz/en/reference/messaging-api/#send-push-message) · [Retries](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)
5. **Qualify alternatives.** Run the same capability fixtures for OpenRouter, Claude, and OpenAI. Keep one active connection per Project. Switching requires an Owner and a passing test. Fence queued analysis against the connection revision so it cannot silently go to another provider.

## Release checks

- Verify both Thai and English, a screenshot, and a PDF. Exercise invalid keys, inaccessible models, quota limits, provider outages, and failed key rotation.
- Use a disposable backend and a test LINE channel. Check replay, out-of-order events, expired and unsent files, cross-Project and cross-chat access, stale Ticket versions, and retry after an uncertain push. Expect a single Ticket operation and a single accepted push.
- Keep LINE and external model calls disabled in the named-account pilot. Live opt-in depends on approved provider data handling, a clear chat notice, spend caps, and Project and chat pause controls.
- Measure two setup submits for an existing approved chat and one staff submit for each complete suggestion. Start with staff approval for every Ticket change and outgoing reply.
