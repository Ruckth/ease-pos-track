# Customer usernames, Project invitations and recovery

## Adopted launch scope

Customers join with a Project invitation and can access only their own active Tickets in active Projects. Apply one password policy across signup, change and recovery. Check Thai and English enrollment, independent abuse limits and accessible loss recovery. [Decision register](../../architecture/t3code-phase1/launch-contracts.html#decisions) · [Customer visibility and password rules](../../architecture/t3code-phase1/launch-contracts.html#customer) · [Enrollment, recovery and accessible operation](../../architecture/t3code-phase1/launch-contracts.html#customer-ux) · [Recent proof for sensitive actions](../../architecture/t3code-phase1/launch-contracts.html#identity).


Customers join a Project with a single-use invitation, choose a username and password, save a recovery code, and open their own Tickets. Email is optional. Use the same Convex Auth v2 core as staff and its username/password components. The app owns invitation rules, customer records, Project membership, recovery authorization and Ticket visibility. [Username guide](https://docs.convex.dev/auth/convex-auth/methods/username-password) · [Method API](https://docs.convex.dev/convex-auth-api/methods/username-password/server/).

## First use and returning customers

An Owner creates an expiring single-use invitation for one Project. Deliver it to the intended person through a known contact or in person. The invite is transferable until redeemed. Opening or previewing the URL never consumes it. On the join screen, show the Project and the active identity before confirmation. A returning customer signs in to add the Project to their existing customerId. An existing member sees their membership without using up the invite. A staff session must switch account before enrollment.

Customers choose an account-wide username of 3–32 ASCII letters, digits, underscores or hyphens with at least one letter or digit. Trim and lowercase on the server, reserve system names and show the resulting username before submission. Keep disabled names reserved. Allow a Thai or English display name and Unicode passphrase. Provide visible field labels, password manager support, keyboard focus, specific invite errors and a generic sign-in failure in both languages. Test at phone and desktop widths. Ask Thai pilot users to complete joining and recovery unaided to verify the chosen alphabet for launch.

## Enforce signup on the server

Register a gated application signup mutation through the approved auth policy. Base it on the pinned v2 method using core.bindMethod and the mounted components. The stock exported signup accepts username and password only. Expose only the guarded entry point. In one mutation validate the invite digest, Project state, account context, username and password. Use the v2 username mapping and password component to create the verified credential, customerId, session admission and membership together. Consume the invite only with a successful commit. Any unexpected component failure after creating the principal must roll back the entire transaction. The existing-account join path requires a live customer session. A lost success response can be recovered by signing in with the chosen credentials and reading current membership. Offer authenticated generation of a fresh recovery code if the first display was lost.

Use 15–100 Unicode code points on every password write, and reject common or compromised choices through reviewed component policy. Preserve the user's Unicode password behavior consistently on creation, verification and reset. Use isolated per-account progressive backoff, protected ingress limits where supported, and separate recovery capacity. Verify unrelated customers retain access during abuse. Never trust a caller-selected client ID as the sole limit. Budget expensive work before hashing. Mask unknown, disabled and wrong-password responses at the backend, including raw RPCs. Record rejected attempts using committed outcomes. Exercise concurrent failures, timing differences and honest recovery after throttling. [NIST password guidance](https://pages.nist.gov/800-63-4/sp800-63b.html) · [Existing customer handlers](https://github.com/Ruckth/ease-pos-track/blob/f74576308213563648934d1058ed5f079a27936f/convex/customers.ts).

## Recovery without email

Use a one-time, cryptographically random 128-bit saved recovery code, stored as a digest bound to the immutable customerId and credential generation. Reveal once on authenticated setup, with copy/print instructions and a reminder to store it away from the shared device. Regenerating it with recent authentication invalidates the previous code. Once assisted recovery is enabled, a signed-in customer can optionally enroll a verified business recovery contact while they have access. The UI distinguishes normal password change, which requires the old password, from lost-password recovery.

For lost-password recovery, the person enters username, recovery code and new password. Use a rate-limited auth mutation that verifies the digest, active customer identity and expected generation. Reset the credential on that same auth user through a reviewed server-only component adapter, consume the code, increment the generation and revoke all existing sessions in the same successful transaction. Never expose the password component's privileged setter as a client endpoint. The token and new password must never enter analytics, error details or command history. Require fresh sign-in to obtain a replacement recovery code. A lost response is reconciled by testing the new password. Concurrent submissions can produce only one reset.

The v2 username recipe provides authenticated changePassword. The proposed recovery transaction is app work. In 2.0.0, inspect the published username and email method sources for the password write and the core's revokeAllSessions helper, then prove that the guarded adapter works with the pinned release on the disposable backend. If that proof fails, pause enrollment and redesign the recovery adapter before shipping. During the pilot, loss of both secrets has no same-account recovery path. Later assisted recovery requires independent identity proof and audited Owner approval. Without sufficient proof, issue a new invitation for a separate account and retain the original Ticket ownership. [Pinned package source](https://unpkg.com/@convex-dev/auth@2.0.0/src/methods/email-password/server.ts) · [Recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

## Support-assisted reset after the pilot

At that checkpoint, auth:openSupportCase is a feature-gated browser mutation for active support staff holding the Staff or Owner role and assigned the support duty. Bind the case to its actual staff requester. A separate Owner approves. App authorization never follows from the internal title “support”. Deny raw, key, customer and unauthorized staff calls. The four public assisted-recovery routes stay absent from the minimum pilot.

Store a deployment-scoped assisted-recovery feature generation. Every enable or disable advances it atomically. Capture the current enabled generation on the case, approval and grant. Inside auth:redeemSupportReset require the feature to be enabled and all recorded generations to equal the current one, alongside existing contact, account, expiry and digest checks. The feature switch and password change share a serializable transaction boundary. Feature-off disables opening cases, approval and redemption; operator incident revocation and audit cleanup remain available internally. Re-enabling cannot revive an old case, approval or secret. Open and approve a new case under the new generation.

Test issue → disable → redeem → re-enable → retry the original grant. Both redemptions must leave the password, saved code, sessions, generation and ownership untouched. A freshly approved grant after re-enabling succeeds once. Race disable with redemption: a reset committed before disable records one result; a reset ordered after disable fails with no effects.

The minimum pilot implements saved-code recovery only. When both password and code are lost, explain that a new invitation creates a separate account; existing Ticket ownership stays with the original account. The person can decline the new account. Keep ordinary support cases, contact records, approval UI and reset grants outside the pilot schema and route allowlist. A deployment restore has a separately audited, internal-only, two-person quarantine procedure that preserves proven customer ownership. Ops can log an anonymous count of unmet recovery needs. Introduce assisted recovery only after a real support need is documented, the privacy lead approves contact handling, and two trained people and a private handover method are available. Existing customers can enroll a verified contact after authenticating while they still have access. No contact can be added retrospectively by a locked-out claimant.

After the assisted-recovery feature is enabled, an authorized support staff member opens a case and records their own staffId as requester. Only the public Owner-only mutation auth:approveSupportReset can approve it. It consumes fresh action-bound proof for the exact case, beneficiary, contact version and intended change, checks the requester and approver are different active humans, then invokes the internal issue operation in the same transaction. The public auth:revokeSupportReset requires the same role and fresh proof. Neither endpoint operates while the feature is disabled. Test staff-only, self-approval, stale or missing proof, direct internal invocation and feature-off denials.

A customer who enrolled a verified independent recovery contact may request assistance when both password and saved code are lost. Support verifies the request against the previously recorded business contact through a known channel and confirms the customer's identity out of band. Record the contact reference, verification version and outcome without copying private correspondence. A different human with the Owner role reviews the evidence and supplies the action-bound proof to authorize issue. Staff cannot issue an unreviewed reset. If independent verification or a second reviewer is unavailable, offer a new invitation for a separate account and retain the original ownership.

The internal issue operation generates a random 128-bit one-use secret. Store a keyed digest with the support case, immutable customerId, auth user ID, credential generation, verified contact ID and version, approving Owner ID and expiry within 24 hours. Invalidate any older grant. Hand the one-time value directly to the verified customer in person or by a previously verified private channel under their control. An independent business verifier can attest identity but does not receive the customer's credential. Never use a destination supplied only in the recovery request. The Owner can revoke a grant; replacement, disable, password/code reset, altered contact, a superseding grant or expiry invalidates it. Omit the secret from support notes and logs.

On the public purpose-allowlisted auth:redeemSupportReset mutation, accept the account handle, grant selector and secret and a new password. Resolve the immutable account, check the digest and all bindings, active status and expiry, and use the same atomic password change, generation increment, saved-code invalidation and all-session revocation as saved-code recovery. Consume the grant on successful commit. No session is issued by redemption. Use isolated request throttling and masked failures. After a lost success response, sign in with the new password and generate a fresh saved code. Recovery never transfers Tickets to another principal.

Add the endpoint and its credential class to the architecture tests. Verify expired, revoked, wrong-account, changed-contact, stale-generation and replay attempts via raw RPC; race two valid redemptions and disable against reset. Inject failure after setting the password. Expect the old state intact on failure, one committed reset on success, old sessions denied and original Ticket ownership preserved.

## Ticket privacy, credentials and account switching

A live auth user maps to one active customerId. Every Ticket read, list, search, count and write enforces active Project membership, active Ticket and customer ownership. Pilot media routes stay closed. Same-Project peers cannot infer one another's Tickets. Hide archived Projects and Tickets on every customer surface, including notification and media access. Scope create/attach receipts to the durable actor and original Project. Preserve protected media reservations across reset and disable. A staff assignee, a staff email match or possession of a request ID cannot acquire a customer's Ticket. Use a single-use action proof for sensitive account changes. On sign-out clear subscriptions, draft previews, cached content and local authentication material before showing another account. ## Acceptance before the first invitation

The identity implementer demonstrates one Owner and two customers in the same Project, plus a second Project. Test simultaneous invite redemption and normalized username collision, expired/revoked invites, direct calls to legacy registration, lost signup response and replay after password recovery. Verify identical denial on cross-customer direct reads, media, search and counts. Disable the account while a session is open, try to use a pre-reset token and refresh token, and switch between staff and customer on the same shared device. Assert denial at the server and absence of cached Ticket content. A customer with zero email addresses must complete the whole journey.

The release owner records the local handler and browser results, including a failed reset that leaves the old password, code, customer ID and Tickets intact. The recorded starting condition is zero users. Introduce the new browser flow before inviting anyone. Retire legacy email/password signup and the shared staff login, preserve any non-user data, and keep external messaging disabled until its own release checks pass.
