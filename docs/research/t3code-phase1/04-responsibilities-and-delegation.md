# Assign Tickets by responsibility and add scheduled suggestions

The broker and scheduled assignment sections describe future design. The
zero-user launch uses manual assignment and staff-reviewed local rules. Follow
the [active Ticket routing instructions](../../ticket-routing.md) for launch
behavior and the approved-dataset requirement.

Manual assignment delivers value before any AI is enabled. The selected T3 agent can later suggest a responsibility area. Track Ease checks eligibility and selects the person from that area.

## Manual routing in the pilot

The Owner creates Project responsibility areas and an ordered roster of primary and fallback staff. Staff set their own availability and away-until time. Owners manage other people’s eligibility with an audited reason. An authorized staff member can assign, reassign, unassign or hold a Ticket. Record one optional area and assignee, source, staff ID and Ticket version. Area membership grants no Project access. Expose Mine and Unassigned views. Owners choose at least one active intake staff member for each pilot Project and designate a backup.

For example, a customer opens a Ticket about a receipt that did not print. Intake staff assign it to an available printer specialist. The customer sees the Ticket status. Other customers cannot see the Ticket, the internal assignment reason or the staff roster. An unavailable assignee flags existing work for review. Keep manual overrides and holds through subsequent T3 runs.

## Try a routing rule before running an agent

Freeze a separate, untouched holdout of at least 50 distinct residual cases where the tuned rule abstains or conflicts, disjoint from all rule-authoring and tuning examples. Freeze expected area labels with staff before scoring. Use only these residual cases for the broker decision. Report their frequency in the overall pilot separately so a rare residual cannot justify a costly service. Score each approach on the identical residual set with the same denominator, including every error and abstention. The rule keeps its confident exact matches. The selected agent is a candidate only for the residual queue. A minimum 10-point improvement means five additional correct routes on exactly 50 cases. Equal or lower wrong-route rate, a positive improvement, and budget approval are all required. Test the gate on 49 cases, a tie, worse errors and insufficient improvement (off), and on 50 cases with a ten-point gain, equal errors and approved budget (eligible for broker work). Keep the rule until this evidence exists.

Start with an Owner-maintained, versioned mapping from a product/symptom pair to one responsibility area. A unique active match creates a suggestion in the app. No match, conflicting rules or restricted input stays manual. The same review queue and version checks serve rule- and agent-generated suggestions. With zero users, the default is manual work followed by this inexpensive rule. The signed doctor-only T3 connection remains a separate deliverable that the team can use without buying model capacity.

Collect closed, non-sensitive examples, tune the rule on the development set and freeze its revision. Reserve the independent residual holdout defined above. Measure correct actionable suggestions per example, wrong suggestions, abstentions and operator corrections. If the rules cover 90% or more correctly, keep the rules. If they fall short, first correct obvious gaps in the mapping. A sustained residual gap is a reason to evaluate the user-selected agent on a disconnected, synthetic or explicitly approved sanitized fixture using the same codes. Record input eligibility, provider terms, spend ceiling and sample split before that comparison.

Proceed to broker implementation only if the agent improves correct coverage by at least 10 percentage points over the tuned rules on the held-out set, has no higher wrong-route rate, and its projected cost fits the Owner's approved cap. An inadequate sample, a tie or lower quality keeps the broker off. This comparison grants no live Ticket access. If the team never reaches this gate, keep manual and rule suggestions plus the T3 connection. Scheduled initial autoassignment has a further release gate: after suggestions run successfully, two staff reviewers independently label at least 100 consecutive distinct in-scope candidates before seeing model output. Count incorrect answers and abstentions in the denominator for correct coverage. Require at least 95% correct, zero data-policy violations, and tested pause/override behavior. Exclude restricted Tickets from all provider inputs. Resolve reviewer disagreement manually and record it. Audit the denominator, source and change in case mix before each expanded rollout.

## Reviewing a suggestion

The Project has two routing configuration fields. policyGeneration advances atomically on every change to mode, sponsor, allowed provider/data policy, roster, availability configuration or mapping. ruleRevision identifies the product/symptom mapping itself. A mapping or vocabulary edit advances both in the same transaction. A roster-only edit advances policyGeneration and leaves ruleRevision alone. Both values are monotonic. Ticket version, membership visibility, credential generation and run fence have separate purposes. Even with equal revisions, evaluate time-dependent availability and current authorization again at use.

The canonical proposal key is (source, Project ID, Ticket ID, Ticket version, policyGeneration, ruleRevision). Persist all six fields. Also bind a caller request ID to its original immutable key and input digest. Replaying an authorized request for old rule A can return only its original stale record; it cannot become a proposal for rule B. After a mapping edit, a fresh request under B on the unchanged Ticket creates exactly one new proposal. A second equivalent request resolves to B. Only B can be accepted once if it remains eligible. Repeat for local and AI sources, and race a rule edit with submit and accept.

The built-in rules and a T3 run in suggestions mode create only a staff-visible proposal. The separately promoted initial-autoassignment mode uses its own operation. Store a suggestion ID, source, Project, Ticket and expected version, policyGeneration and ruleRevision, proposed area, short enum reason, request identity, creation/expiry and status. Deduplicate using the full six-field proposal key above. Preserve the original result for equivalent input; reject changed input under the same identity. Keep pending suggestions in the staff review queue for 24 hours. Submission leaves the assignee, Ticket version and assignment event stream untouched.

An authorized staff member can accept or dismiss a pending suggestion. In one transaction, acceptance invokes the ordinary manual assignment domain operation under the human's identity. Recheck current Project access, live Ticket, expected version, no hold, empty assignee, current policy/roster and eligible area/member. On success write exactly one manual assignment and event plus suggestion acceptance and receipt. On conflict mark it stale and leave the Ticket alone. Dismissal, expiry and supersession create no assignment or customer-facing event. A duplicate accept returns the original result to an authorized caller. A reviewer can always ignore the suggestion and assign manually.

Test duplicate submission, concurrent accept/dismiss, two reviewers accepting, manual assignment and a hold racing with acceptance, and roster or access changing before review. Verify that a suggestion never changes the assignee by itself and that a stale submission cannot overwrite a person's choice.

## Which operation each routing mode permits

Validate the run and UTC-day limits in the same transaction as assignment. The shared routing-authority contract defines the caps and the concurrent-winner and replay tests. [Authoritative limits and tests](../../architecture/t3code-phase1/launch-contracts.html#authority-modes)

The Owner configures one versioned policy per Project with paused, suggestions or initial autoassignment mode. Manual assignment is a separate human operation in every mode. Rule-based routing always produces a reviewable suggestion. In suggestions mode the T3 broker can read the approved projection and submit a staff-only suggestion. Only an authorized human can accept it through manual assignment. Attempts to call the initial-assignment operation in suggestions mode fail before changing any Ticket, version, assignment event or receipt for a new write.

To promote, the Owner uses current action-bound proof, records the quality, privacy, operator and spend evidence, and explicitly enables the separate initial-assignment grant for that broker and Project. Promotion, demotion, pause and any policy configuration change atomically advance policyGeneration and invalidate run grants, leases and pending automation proposals from older generations. A suggestion cannot convert into an automatic write. A pending old suggestion becomes stale. Promotion issues no implicit key or wider permissions. A new run must verify the actual selected provider and current credential, obtain a fresh fence, and fetch a newly authorized candidate. Human holds and manual assignments always win.

In initial autoassignment mode the broker submits only a candidate alias, chosen approved area alias and closed reason code. A dedicated initial-assignment mutation, separate from suggestion submission and human acceptance, atomically verifies the explicit broker write grant, active mode and exact generation, original activation cutoff, live sponsor and fence, eligible Ticket version and status, no human hold or assignee, roster and budget. Track Ease chooses the eligible person, then records the assignment, version, staff-only event and stable idempotent receipt once. The external model never selects a person or sends a notification. Ineligible, uncertain or drifted results leave the Ticket unchanged. No automatic reassign, unassign or status change.

A paused or demoted run cannot create a new assignment on retry. An already committed assignment remains historical and cannot be undone by replay. Authorized receipt reconciliation may show its original outcome through a separate read without repeating the assignment; a disabled key is denied even that read. Race promotion, demotion, pause, human hold and duplicate submission against each mode. Verify no side effects in suggestions or paused mode, at most one initial assignment for an eligible newly promoted run, and no additional versions, events or budget use from an expired run.

## Which Tickets can enter any scheduled sweep

Use one server eligibility function for candidate fetch, the last check before provider disclosure, broker suggestion submission and automatic assignment. Re-evaluate the currently enabled, versioned local rule against the current Ticket product/symptom codes. Only an abstention or conflict is eligible for external AI. A unique confident match stays entirely within Track Ease. Also require a post-cutoff Ticket, matching Project, current data-policy generation, explicit disclosure permission, unrestricted classification, current Ticket and rule versions, appropriate policy mode, sponsor and live fence. Capture the ruleRevision and policyGeneration in the candidate grant. Editing a rule advances both ruleRevision and policyGeneration and invalidates the old grant. An epoch match alone never substitutes for evaluating the rule and privacy predicate. Rule-generated local suggestions do not require AI eligibility.

With two otherwise eligible post-cutoff Tickets, one matched and one conflicting, the fake provider must receive only the conflicting alias. A forged submission for the match and an old submission after a rule edit resolves the conflict must create no suggestion, assignment, event or budget charge. Re-test rule or sensitivity change between fetch and disclosure, between disclosure and submit, and on receipt replay. Block further disclosures or writes after a change; preserve history for any batch already delivered. The residual baseline abstains and makes zero wrong routes, so the agent must make zero wrong routes on the frozen comparison. Fifty cases with six correct and one wrong keeps the broker off.

When a Project enables scheduled suggestions for the first time, capture an immutable activation Ticket-number cutoff equal to the last number allocated by ticketCounters for that Project (nextNumber minus one), or zero when no counter or Tickets exist. Read the Project counter in the activation transaction so concurrent creation serializes against it. A missing counter with existing Tickets fails closed for operator reconciliation. Keep that cutoff on a durable Project routing record outside individual policies, runs and sweep cursors. A Ticket is eligible only when its original immutable Project identity matches and ticketNumber is strictly above that cutoff. Recheck on every fetch, suggestion submit and scheduled initial assignment, in addition to current privacy, status and access. Each sweep's high-water mark limits the upper end of the scan and never changes the lower cutoff.

Pausing, restarting, replacing a key or policy, relabeling, restoring, reassigning a sponsor, or beginning a new sweep cannot backfill older Tickets. Retain the original cutoff across cleanup and compatible restores. If it is missing or the allocator regresses, stop the Project's automation and reconcile against retained history. No per-Ticket historical override in Phase 1. Staff may label older Tickets for manual work or local rules; sending them to a provider stays prohibited. Test a labeled pre-activation Ticket and an equivalent post-activation Ticket across two sweeps, revisions, pause/resume and restore. Assert absence of the older alias in captured provider inputs and denial of a forged write. Race creation with activation and verify the committed allocator order determines the outcome.

## Prepare data and select the actual agent

Before AI, the Owner configures an allowlist of product and symptom codes, their safe descriptions and eligible area codes. Provide bilingual dropdowns and an explicit Restricted control at Ticket entry and staff review. Default an unknown value or missing review state to manual. A durable Project activation cutoff excludes earlier Tickets from every scheduled sweep, fetch and write. A policy names a single Project, sponsor, allowed areas, provider instance, model/options, host, workspace, interaction/runtime modes, versions, data-policy terms, budget and expiry. Start in suggestions mode. Initial autoassignment requires a separate Owner decision after examples match the team's expectations.

Use T3 new-thread scheduled runs with a selected model and the verified dedicated workspace. Begin with a 15-minute interval on an awake enrolled macOS host. A bound thread may follow its current model; exclude it at this checkpoint. Dispatch can start a provider turn even if the queue is empty. A stopped host may miss work. The server records actual completed runs, not just successful dispatch. Test settings, scheduler and observed run metadata on each installed version. ## What the scheduled tool can do

Run the signed broker under a dedicated macOS service user with its own Keychain item. The model's OS user gets only a fixed local tool that calls a permissioned Unix-domain socket. Verify peer UID, enrolled process/session and T3 occurrence through a trusted host control interface. The model-facing socket can request preflight and an authorized fetch only. It exposes no submit or finish command. A separate authenticated provider-response channel forwards the single terminal reply to the broker. Only the broker validates it, submits results to Track Ease and finishes the run. Do not offer generic shell, CLI proxying, arbitrary paths or forwarding. The broker independently reads actual provider, model/options, host, workspace and runtime. A client-supplied run ID or saved schedule alone confers no access. A compromised host is outside this attestation boundary. Missing verifiable metadata or OS isolation holds this integration.

The broker authenticates only to the dedicated gateway. Preflight discloses no data and acquires no lease. After T3 has started the turn, the first authorized fetch atomically verifies the server nonce, runner, current sponsor, exact approved configuration and policy generation, claims a new fence, starts the lease and returns the first projection. Two simultaneous fetches yield data to one winner only. A crashed preflight leaves no lease. Further reads and writes check that same fence and current policy. Renew a 180-second lease every 60 seconds under a 10-minute total cap. At expiry the old fence has no authority. Check controlled-clock boundaries and late writes. ## Final batch disclosure and pending suggestions

The authorized provider request containing a projected batch is terminal for that classification turn. Use a single schema-validated structured response with candidate and area aliases or uncertainty. The broker parses it, submits the eligible outcomes to Track Ease under the existing run, reconciles receipts, and calls finish automatically. The model does not need a second upstream tool-use turn. The host adapter handles any SDK continuation locally with a terminal tool acknowledgement or end-of-turn response; it strips Ticket-derived bytes and makes zero upstream requests. Verify the actual Claude/Codex provider protocol. If local termination cannot be supported and proven on that installed combination, leave broker routing disabled.

Judge run success and the consecutive-failure counter by Track Ease’s committed, idempotent finish receipt. T3 UI and provider turn statuses are separate telemetry. A deliberately blocked follow-up has no effect on a successful finish or the failure count. A failed parse, un-reconciled commit, missing finish or stale fence is recorded as failed, partial or unknown under its original run and never counted as a completed success. Recovery may reconcile original receipts and finish a still-authorized run without resending to the provider. A late finish cannot acquire a new fence or duplicate an assignment.

In the positive host test capture exactly one upstream request with aliases, one authorized suggestion or conditional assignment, and one committed finish. Simulate the provider driver asking to send the tool result upstream: the local terminal response sends zero bytes, Track Ease shows completed, and the failure count stays unchanged. Include this path in 40 representative nonempty runs per advertised combination; at least 95% must reach committed finish within the cap. Repeat crash-after-submit, duplicate response and lease expiry with no repeated upstream transmission.

There are two observable AI boundaries. First, the isolated broker releases one approved sanitized projection into the selected T3 turn. The moment T3 can read the tool result, the projection is disclosed to T3 and its permitted transcript. The broker must initiate that handoff within five seconds of its committed one-use authorization. A later upload from T3 to an external model is a separate disclosure. The first authorization never travels with cached tool output and gives no right to upload it later.

Require a tested provider-egress adapter as the only route for a turn containing Ticket-derived fields. Before a provider upload it obtains a fresh one-use provider-send permit for that batch and destination using the current policy, fence, eligibility and exact projection digest. Consume the permit at the final transport under the same five-second initiation bound. Permit at most one provider submission per disclosed batch; no SDK resend, transcript replay, secondary provider, continuation or model fallback can resubmit it. Treat an ambiguous send as already disclosed. If the T3/provider combination cannot gate every path, prevent the first T3 handoff and keep manual/rule routing. This is a later host compatibility condition; doctor needs neither adapter nor provider access.

Test a recording T3 transcript and provider separately. Suspend after the broker handoff and before provider authorization, advance beyond five seconds, pause the policy, then resume. Expect one prior T3 transcript entry, zero provider uploads, and zero new handoffs. If provider authorization committed before suspension, resume after expiry still yields zero uploads. In a fresh positive run with current authorization, allow one handoff and one timely provider upload. Replaying the tool output, restarting the provider session or attempting a second model call must add no transmission. A change after an actual permitted upload cannot recall bytes already delivered.

The dedicated broker may privately stage a projected batch after first fetch. Before any model-facing socket reply, stdout, transcript or provider payload, consume a fresh one-use disclosure authorization for the exact batch under the shared external-action contract. Its commit is the policy ordering point. A change committed first releases zero bytes. When authorization wins, at most that one exact bounded handoff may finish. Test both orderings with a fake provider and a suspended broker. Any later write must still pass current mode and eligibility.

Rule edits advance both ruleRevision and policyGeneration and mark outstanding automated proposals stale. On acceptance, re-read ruleRevision, policyGeneration, suggestion source, Ticket version and current policy in the manual transaction. Recompute the residual predicate for AI proposals; reject a formerly conflicting case that now has a unique local match. The staff member can still assign independently by making a new manual choice. Built-in rules remain review-only in this pilot so staff can learn and correct their mapping. The later AI-only initial assignment is a separately measured and deliberately granted capability. A successful AI comparison never promotes a rule or a pending suggestion. [Ordering and race tests](../../architecture/t3code-phase1/launch-contracts.html#external-io)

## Inputs, outputs and human control

The model receives only a per-run candidate alias, approved product/symptom codes and eligible area aliases with their controlled meanings. Track Ease holds the mapping to Tickets and people. No raw Ticket text, staff names, contacts, media, external URLs or free-form notes. Return one candidate alias and one eligible area alias or an explicit uncertain result. Any reason is a closed enum such as configured_match or ambiguous. Reject extra fields, arbitrary text, invalid IDs and oversize outputs. Restricted, sensitive or unclassified Tickets yield no provider payload. The broker resolves the alias and Track Ease selects an eligible person deterministically.

Capture a stable per-Project Ticket-number high-water mark. Scan up to 100 rows, return up to 20 candidates, cap input at 64 KiB and output at 16 KiB, and apply the shared per-run and daily assignment caps transactionally. The backend records page outcomes before advancing its cursor and periodically starts a new sweep. In one transaction recheck authority, version, active Project, initial unassigned status, human hold, roster and budget, then append the assignment, staff-only event and idempotent receipt. Retain the same request ID and owner for a lost response. A stale or uncertain suggestion leaves a Ticket for staff.

Before enabling writes exercise pause, sleep, stale metadata, sponsor disable, key expiry, duplicate/lost responses, concurrent staff edits, invalid projections and private-channel canaries. Test 40 representative nonempty runs on each supported combination; at least 95% must finish before the configured deadline. If throughput or isolation fails, keep the manual workflow. The backend alerts Owners about stale heartbeats and expiration, independent of host uptime. To stop, pause the policy and invalidate the fence first, then disable the timer and reconcile outstanding receipts. ## Alternatives and operating evidence

A server-triggered AI worker could operate while local T3 is offline, but needs its own provider credentials, integration and support model. The user-selected T3 environment is the default for this release. Require a verified provider-side spend cap or explicitly approved capped account before unattended operation. Reject broad tool permissions and retain synthetic input/output captures with the tested host manifest. Use Convex serializable transactions for conditional assignments and current-access checks.
