Track Ease and T3 Code launch plan

Launch with Google sign-in for invited staff, usernames for customers, manual Ticket assignment and an in-app inbox. That is enough to serve the first two customers.

Researched 15 November 2026 · Launch decision updated 19 November 2026 · Track Ease source f745763 · Recommendations only · Research and plan review

Recommended direction: Convex Auth v2 with invite-only Google sign-in for staff and username/password for customers, a scoped CLI and skill connection to T3 Code, optional scheduled initial assignment, and app-controlled notification preferences.

The signed T3 connection, optional email and LINE can each ship separately. Add scheduled AI assignments only if the selected model improves on the team’s routing rule.

The five topic plans

Staff accounts and Google sign-in Identity foundation

Invite named staff through Convex Auth v2 Google sign-in. Track Ease assigns durable staff IDs and enforces Owner and Staff permissions.

Designate the first Owner explicitly. Prove revocation across browser sessions, personal keys and scheduled assignments.

Staff identityImmutable staff ID survives login changes, key rotation and deactivation. A credential ID explains how someone acted.
Customer ownershipKeep customer IDs, Project membership and individual Ticket ownership. A staff assignee never replaces the customer owner.

Important corrections to the earlier combined draft

The Product Owner (accountable role) confirmed there are no existing users. One Convex Auth v2 core handles both browser sign-in methods. Account migration is outside the initial release.

Connection: reuse the existing CLI contract. A downloadable package, key importer and connection doctor are proposed work. Secure one-use entry does not itself create a durable scheduled credential.

Scheduling: the inspected scheduler treats bound and new-thread runs differently. Record the actual provider selection and workspace; dispatch status is separate from a committed Ticket assignment.

LINE: use Messaging API and documented account linking. The official Thailand notice confirms a Reply API change from 1 February 2027; it is distinct from push-message pricing. Check the chosen account’s current terms before enabling LINE.

Build order and release gates

  1. Open the smallest usable pilot. First prove pinned Auth session issuance and admission locally and inventory all 36 existing protected registrations. Then configure the dedicated staff identity sender and verified domain. Verify the first Owner, customer enrollment and recovery, then close legacy access through the single cutover gate. Deliver text-only Tickets, manual assignment and the authenticated inbox. The signed T3 kit comes at the next checkpoint. A customer can open a Ticket, staff can take it, and the customer can see progress.
  2. Open the T3 connection checkpoint independently. Publish the signed kit and prove its doctor-only gateway on each supported host. Shipping this connection does not require an AI routing experiment.
  3. Test whether AI improves routing. Use an in-app product/symptom rule first. Measure the selected agent on at least 50 separate residual holdout cases before investing in a broker. If it qualifies, record host and actual dispatch evidence, validate the approved data projection and run the manual override, timing and revocation tests. The Owner can enable limited initial autoassignment afterward.
  4. Add optional external channels. Release verified Ticket email after consent, privacy and delivery checks. Enable LINE at checkpoint 1b after proving external-browser linking, quotas and replay handling. Both channels open the same authenticated inbox.

The release checklist names accountable roles and evidence. The cutover and rollback procedure covers retained operational data. A separate restore procedure invalidates old access before reopening.

First pilot and release evidence

The smallest pilot has an Owner, an independently recoverable backup Owner, a named Staff member, two customers in one Project, and a second Project used to test isolation. A customer joins by invitation and creates a Ticket, a staff member assigns it manually, and the customer sees its status. At the next checkpoint, doctor proves the named connection without accessing any Ticket. The Owner can retain the built-in rule indefinitely. A T3 runner requires a measured improvement and a verified host.

The implementation lead records the code revision, pinned versions, fixture set, results and unresolved failures for each topic. Use pnpm agent:setup in an isolated checkout, pnpm convex:local for schema work, pnpm check and pnpm test:browser. For the new delivery tests, use fake providers and block outbound traffic as the existing upload tests do. Record real Google redirect and supported T3 provider/host results separately. The provider operator checks real email and LINE with designated consenting pilot recipients only when that channel is approved.

Release each capability after its documented gates pass. The Owner checks new invitations, failed recoveries, the unassigned queue, stale runner health, suppressed deliveries and unresolved outcomes during the pilot. Pause enrollment for identity failures, revoke a compromised key, pause the assignment policy for routing failures and pause external delivery for channel failures. Keep manual Ticket work available where authorization is intact.

Operating decisions before rollout

The decision register records each launch default, its owner, the release it blocks and the evidence still needed. Real provider accounts, host versions, privacy approvals and rollback builds are supplied by the accountable operator before enablement.

Five sequential research tasks; one topic per task. Each plan includes claim-local primary sources and code references.
